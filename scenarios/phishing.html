Phishing URL Detected

When this alert appears, the first thing I want to know is whether the user actually interacted with the phishing URL or whether the connection was blocked before the page loaded. Many phishing alerts are harmless delivery attempts, while others become full account compromise incidents.

Important: The investigation should focus on understanding how far the attack progressed rather than only confirming the URL is malicious.

Step 1 — Validate The Alert


I would begin by reviewing the SIEM alert details and collecting the basic information related to the event. At this stage, the goal is to understand who triggered the alert, when it happened, and which security product detected it. Proxy logs, email security alerts, DNS logs, and EDR telemetry usually provide the initial evidence needed for triage.


Main things to verify:

  • Username and hostname
  • Full URL and domain
  • Detection source
  • Timestamp
  • Allowed or blocked connection


Where to look:

  • SIEM timeline
  • Proxy/Web gateway logs
  • Email security platform
  • DNS security logs

Step 2 — Confirm User Interaction


After validating the alert, I would check whether the phishing page was actually accessed successfully. A blocked request is far less dangerous than a successful HTTP 200 response. Redirect chains are also important because attackers often hide phishing infrastructure behind multiple redirects or shortened URLs.

At this stage I focus heavily on browser activity because it tells me whether the attack moved beyond delivery into execution or credential theft territory.


Main things to focus on:

  • HTTP response codes
  • Browser history
  • Redirect activity
  • File download attempts
  • Multiple connection attempts


Where to look:

  • Proxy logs
  • Browser history
  • EDR web activity
  • Secure web gateway logs

Step 3 — Investigate Endpoint Activity


Once user interaction is confirmed, I move directly to endpoint investigation. This is usually the most important part because phishing becomes dangerous only after execution or credential theft begins. I carefully review the process tree to identify suspicious child processes spawned from browsers or email clients.

Critical Indicator: Processes like PowerShell, cmd.exe, mshta.exe, wscript.exe, or rundll32.exe launched from Chrome or Outlook immediately increase the severity of the alert.

Main things to focus on:

  • Process tree
  • Script execution
  • Downloaded payloads
  • Suspicious child processes
  • Newly created files


Where to look:

  • EDR telemetry
  • Sysmon logs
  • Windows Event Logs
  • Temp and Downloads folders

Step 4 — Check For Credential Theft


If the phishing page imitated Microsoft 365, VPN, or any authentication portal, I would assume credentials may have been compromised until proven otherwise. Modern phishing campaigns often focus more on stealing cloud access and session tokens than delivering malware.

I would immediately review authentication activity around the same timeframe to identify suspicious login behavior or MFA abuse attempts.


Main things to focus on:

  • Impossible travel logins
  • MFA fatigue attempts
  • New devices or IPs
  • OAuth consent activity
  • Mailbox forwarding rules


Where to look:

  • Microsoft 365 logs
  • Azure AD sign-in logs
  • VPN logs
  • Email audit logs

Step 5 — Look For Persistence Or Malware Activity


If suspicious execution occurred, I would continue the investigation by checking whether the attacker attempted persistence or external communication. Malware delivered through phishing often creates scheduled tasks, registry run keys, or outbound C2 traffic shortly after execution.

This stage determines whether the incident remained a phishing attempt or evolved into a compromised endpoint investigation.


Main things to focus on:

  • Scheduled tasks
  • Registry Run keys
  • Network beaconing
  • External IP communication
  • Antivirus or EDR detections


Where to look:

  • Task Scheduler
  • Registry paths
  • Network logs
  • Firewall logs
  • EDR alerts

Final Investigation Goal


The investigation should always answer four important questions:

  1. Did the user interact with the phishing page?
  2. Were credentials stolen?
  3. Was malware executed?
  4. Did the attacker establish persistence or external access?

Once those answers are clear, containment actions become much easier and the incident can be escalated properly if compromise is confirmed.
